# Digger — архитектура

## 1. Цель
По вырезке фото микросхемы: прочитать маркировку → определить партномер → **найти, скачать, проверить и
подтвердить datasheet** → сверить документ с фото → заключение о памяти (есть/нет, тип, объём, основание).
Главная часть — подсистема получения документов (§4). Всё остальное уже работает в v1 и дорабатывается позже.

## 2. Среда разработки и цель
| | Разработка | Работа |
|---|---|---|
| ОС | **MacBook Pro M4, 48 ГБ (macOS, Apple Silicon)**. Claude Code на Windows 7 не запускается | Windows 7 SP1 **x64**, i5-6500 (4 ядра), 16 ГБ, встроенная графика, **без прав администратора**, `ucrtbase.dll` есть |
| Python | 3.8 arm64 (pyenv или uv), Tesseract из Homebrew | 3.8.10 x64 |
| Интернет | обычно есть | частично закрыт, список сайтов неизвестен |
| Проверка | pytest + CI GitHub Actions (windows-2022, Python 3.8) | ручная проверка после вех, `tools/live_check.py` |

**Поставка на рабочий ПК — портативная папка без установки**: встроенный Python 3.8.10
(embeddable x64) + пакеты + Tesseract (распакованный, с `tessdata`) + программа + `Digger.bat`. Собирает
CI на Windows-машине GitHub, пользователь скачивает архив с GitHub и распаковывает в свою папку (например,
`D:\Digger` или в профиль). Программа пишет только в свою папку (`data/`, `logs/`, `reports/`) и в
библиотеку на сетевом диске; реестр, системные папки и права администратора не нужны.
PDF-библиотека и индекс лежат на сетевых дисках; SQLite-индекс по умолчанию локально (в папке программы),
потому что SQLite на сетевом диске медленный и ненадёжен при блокировках.
Железо: Tesseract запускается параллельно в 4 потока (по числу ядер); интерфейс — Qt Widgets без
требований к OpenGL.

Отсюда следствия: (1) все тесты работают без сети на сохранённых страницах; (2) Windows проверяет CI на каждый
push, а каждая веха (★) заканчивается ручной проверкой на рабочем ПК с Win7; (3) поведение сайтов у пользователя
изучаем по отчёту `live_check`, а не угадываем; (4) на Mac те же версии пакетов, где есть arm64-сборки, иначе —
отдельные версии через маркеры платформы в `requirements.txt` (`; sys_platform == "darwin"`); на Mac нельзя
использовать ничего, чего нет в Windows-версии (код одинаковый, различаются только версии колёс).

## 3. Конвейер (существующие модули v1)
`enhancer → ocr → identifier → local_db → acquire (новое, вместо web_search) → pdf_text → comparator → memory → report`.
Роли и интерфейсы — `digger/core/interfaces.py`, данные — `digger/core/models.py`, выбор реализаций —
`config.json → modules`. Новая подсистема подключается через тот же интерфейс `WebSearch`, поэтому GUI и
конвейер меняются минимально (стратегия «замена по частям»: старый `modules/web/search.py` работает, пока новый
не пройдёт все тесты, затем удаляется).

## 4. Подсистема получения документов `digger/acquire/`

### 4.1 Этапы
```
QueryPlan ─► Discovery ─► Ranking ─► Fetch ─► Validate ─► Extract ─► Verify ─► Confirm ─► Decide ─► Store ─► Learn
(варианты    (адаптеры    (оценка,   (карантин)(PDF цел,  (текст,    (улики,   (независимые (статус)  (библиотека (доверие
 запросов)    источников)  дубли)               безопасен) факты)     баллы)    источники)             + паспорт)  к доменам)
```
Каждый этап — отдельный файл с чистой функцией или маленьким классом; вход/выход — dataclass'ы из
`acquire/models.py`. Любой этап тестируется отдельно.

### 4.3 Модели (главные поля)
- **Lead**: url, title, snippet, source_id, level, kind (`pdf|page|forum|repo`), query, rank_score.
- **FetchResult**: ok, path_in_quarantine, sha256, size, content_type, final_url, error.
- **DocFacts**: pages, has_text, title (метаданные), heading (крупные строки 1-й страницы), producer,
  parts_found{part: [страницы]}, family_patterns,
  packages, manufacturers, ordering_codes, marking_codes, language, doc_type, text_fingerprint,
  ocr_pages (страницы скана, текст которых распознан с картинки).
- **Evidence**: code (`E1…E12`), points, detail (цитата ≤ 150 символов, страница).
- **Verdict**: status (`confirmed|probable|rejected|needs_user`), score 0–100, evidence[], reasons[].
- **AcquisitionRecord**: part, lead, fetch, facts, verdict, sources_agreeing[], stored_path, timestamps.

### 4.4 Проверка (улики и баллы) — таблица в коде + веса в конфиге
| Код | Улика | Баллы |
|---|---|---|
| E1 | точный партномер на первых 2 страницах / в любом месте | +30 / +20 |
| E2 | полный партномер (с суффиксом) в таблице заказных кодов | +15 |
| E3 | партномер покрывается шаблоном семейства (STM32F103**x8**, 24C01/02/04) | +15 (если нет E1) |
| E4 | партномер/семейство в заголовке или метаданных | +10 |
| E5 | тип документа: datasheet +15; app note/errata/каталог −20; страница дистрибьютора −30 | |
| E6 | производитель совпадает с логотипом/префиксом / противоречит | +10 / −15 |
| E7 | корпус с фото есть в документе / противоречит | +10 / −10 |
| E8 | маркировочный код с фото найден в таблице маркировки | +10 |
| E9 | источник: домен производителя +10, известный каталог +5, прочее 0, «плохая репутация» −10 | |
| E10 | тот же документ (sha256 или отпечаток текста) получен из ≥ 2 независимых доменов | +10 |
| E11 | в заголовке доминирует **другой** партномер | −30 |
| E12 | нет текстового слоя (скан), и распознать страницы не удалось | итог не выше `needs_user` |

Жёсткие отказы (сразу `rejected`, файл остаётся в карантине): не PDF, активное содержимое, превышен размер,
повреждён, зашифрован без пустого пароля.
Решение: **confirmed** — ≥ 70 и есть E1 или E3 и нет E11; **probable** — 45–69 (сохраняется с пометкой,
показывается пользователю); **rejected** — < 45; **needs_user** — непрочитанный скан или противоречия.
Скан, страницы которого прочитал Tesseract (`scanocr.py`), оценивается по тем же уликам; в причинах итога —
пометка `ocr_text`.

### 4.5 Подтверждение
Документ «подтверждён», если выполнено одно из: (а) confirmed и скачан с домена производителя;
(б) два confirmed-документа из независимых доменов совпадают по sha256 или отпечатку текста (схожесть ≥ 0.9);
(в) пользователь нажал «Подтвердить». Иначе максимум — «вероятно».

### 4.6 Оркестратор: порядок, бюджет, остановка
- Порядок уровней: локальная база → сайт производителя → базы datasheet → поисковики (англ.) → китайский
  интернет → русский интернет → маркетплейсы → форумы → базы SMD-кодов → GitHub.
  Порядок, включение и запросы — `data/sources.json`.
  Уровни проходятся дважды: сначала сайты (каталоги, производители, магазины — один запрос на источник),
  потом поисковики и запросы через них. Так бюджет запросов не кончается раньше, чем спрошены сайты.
- Бюджет на один чип (настраивается): 60 запросов, 10 скачиваний, 180 секунд. Источник на «отдыхе» после
  капчи в сеть не ходит и запрос не тратит. Сайт, ответивший тайм-аутом, пропускается до конца сеанса
  (`site.slow_skip`), неудача остаётся в заключении.
- Остановка: получено «подтверждено» по §4.5, или исчерпан бюджет, или отмена. «Полный поиск» игнорирует
  остановку по результату, но не бюджет.
- Параллельно до 3 запросов, но к одному домену — не чаще 1 раза в 1.5 с. Капча/HTTP 429/403 → домен
  «отдыхает» 30 мин (запись в здоровье доменов).
- События прогресса (для GUI): `level_started`, `lead_found`, `download_started`, `verdict`, `stopped(reason)`.

### 4.7 Языки запросов
Каждый уровень, где это имеет смысл, ищет на английском, китайском и русском (порядок настраивается,
по умолчанию en → zh → ru). Шаблоны, например: `{part} datasheet pdf` · `{part} 数据手册` · `{part} 规格书 pdf` ·
`{part} 中文资料` · `{code} 丝印` · `{part} даташит` · `{part} документация pdf` · `{code} маркировка smd`.
Поисковик подбирается под язык: en — Google(API)/DDG/Bing/Mojeek/Brave; zh — Baidu/Sogou/360 (Bing CN выключен,
см. «Решения»); ru — Яндекс/DDG/Bing. Ссылки выдачи без партномера (и его семейства) в заголовке, фрагменте и
адресе отбрасываются; если посторонние все — событие `engine.offtopic`.

### 4.8 Наблюдаемость: строка состояния и история на трёх языках
Оркестратор и каждый этап публикуют события в `EventBus` (`acquire/events.py`). Событие хранит **ключ
сообщения и параметры**, а не готовый текст: время, тип, уровень, источник, язык поиска, итог
(`ok|empty|found|fail|skip`), числа. Текст собирается при показе из словаря `data/i18n/{en,zh,ru}.json`.
Подписчики: окно программы, консольный наблюдатель `tools/search_cli.py`, журнал `logs/search.log`, статистика (§4.10).

**Язык строки = язык текущего поиска.** Англоязычные запросы и сайты — по-английски, китайские — по-китайски,
русские — по-русски. Общие этапы (локальная база, скачивание, карантин, проверка, итог) — на языке сайта,
с которого взят файл; итог поиска и сообщения об ошибках программы — по-русски. У каждой строки истории есть
подсказка с русским переводом (наведение мыши), в журнал пишутся обе версии. Значок языка перед строкой: EN · CH · RU.

**Строка состояния** (одна, меняется на лету) и **история** под ней (время, значок ⏳ ✔ ✘ ⤼), сгруппированная
по уровням, плюс счётчики «запросов · найдено · скачано · подтверждено». Пример одного поиска:
```
RU   поиск в локальной базе — не найдено
EN   Searching manufacturer site winbond.com…
EN   Google query: "W25Q64JV datasheet pdf" — no API key, skipped
EN   DuckDuckGo query: "W25Q64JV datasheet pdf" — 7 links found

EN   Searching alldatasheet.com — 1 match found
```

Числа: русский — `ru_plural` (1 вариант, 2 варианта, 5 вариантов, 21 вариант); английский — 1 match / 2 matches;
китайский — счётное слово (个/条/份) без множественного числа. Все ключи должны быть во всех трёх словарях —
тест проверяет полноту. События — единственный способ, которым этапы сообщают о ходе работы.

### 4.9 Хранение
```
<library_dir>/confirmed/<2 символа>/<PART>__<source>__<sha8>.pdf  + .json (паспорт)
<library_dir>/probable/...                                         (+ паспорт)
data/quarantine/<sha16>.pdf.quarantine                            (чистка через 7 дней)
```
Паспорт JSON: part, url, final_url, source, level, sha256, size, pages, doc_type, verdict, score, evidence[],
confirmed_by[], downloaded_at, app_version. SQLite: `files`, `parts`, `acquisitions`, `attempts`
(url, статус, ошибка, время), `domain_health`, `search_cache`, `negative_cache`, `catalog`, `textcache`.
База должна переносить одновременную работу нескольких копий программы на сетевом диске: запись только
через короткие транзакции, `busy_timeout`, SQLite-файл по умолчанию локальный, а библиотека может быть сетевой.
Файлы в библиотеку пишутся через `.part` и переименование; при недоступной папке документ лежит в
`data/library_pending/` (та же раскладка) и переносится при следующем сохранении (`AcquireStore.flush_pending`). Состояние (`library_status`) показывает вкладка «Библиотека» (расширение `library_status`) с кнопкой «Перенести сейчас».

### 4.10 Статистика и адаптивный порядок поиска
**Что собирается** (`acquire/stats.py`, таблицы SQLite `search_runs`, `source_runs`) — по каждому поиску и
каждому источнику: партномер, семейство (из `part_rules.json`), производитель, язык, уровень, запросов,
найдено ссылок, скачано, confirmed/probable/rejected, время до первой ссылки, время до подтверждения,
ошибки/капча, и какой источник **первым** дал подтверждённый документ.

**Показатели источника** (отдельно в целом и по семейству/производителю): доля успеха
(подтверждено / попыток), среднее время до подтверждения, «стоимость» (запросов на успех), доля капчи/ошибок.

**Адаптивный порядок.** Перед поиском оркестратор сортирует источники по ожидаемой пользе
`польза = P(подтверждение | семейство, язык) / (среднее время + штраф за запросы)`, где P — сглаженная оценка
(приор из порядка по умолчанию, как будто у каждого источника уже есть ~5 «виртуальных» попыток — чтобы
новые данные меняли порядок постепенно). Включается после 20 поисков (настройка). Часть бюджета
(по умолчанию 10 %) всегда тратится на «разведку» — источники с малым числом попыток, иначе редкий, но
хороший источник никогда не проявится. Порядок по умолчанию из `sources.json` остаётся запасным; режим
«адаптивный / фиксированный» — в настройках. Причина порядка видна в истории: «порядок: адаптивный, по 37 поискам».

**Отчёт.** Окно «Статистика поиска»: таблица источников (успех %, среднее время, запросов на успех, капча %),
разрез по языкам и семействам, «где datasheet находится быстрее всего», экспорт CSV. `tools/live_check.py`
пишет туда же, поэтому эталонные прогоны сразу улучшают порядок.

### 4.11 Недоступные сайты: защита сайта или сеть производства
Каждая неудачная попытка обращения классифицируется (`acquire/netdiag.py`) — от этого зависит, что сказать
пользователю:

| Класс | Признаки | Что делать |
|---|---|---|
| **Защита сайта** (`site_protected`) | ответ пришёл от самого сайта: капча (reCAPTCHA, hCaptcha, Cloudflare challenge, Яндекс «вы не робот», 百度安全验证), HTTP 429, 403 с заголовками защиты от ботов (cf-ray, server: cloudflare, ddos-guard), страница требует JavaScript, вход в аккаунт, скачивание только по кнопке/таймеру/с капчей | человек в браузере скачать может → ссылка в заключение |
| **Сеть производства** (`network_blocked`) | не разрешается имя (DNS), соединение сброшено или не устанавливается, таймаут до установления соединения, ответ прокси 403/407 или страница блокировки прокси/межсетевого экрана (ищем типовые признаки и название прокси в заголовках `Via`/`Server`), подмена сертификата | нужен доступ → в список для администраторов |
| **Белый список программы** (`not_whitelisted`) | домен не в белом списке | ссылка в заключение; предложить добавить домен |
| **Сбой** (`transient`) | 5xx, обрыв посреди загрузки, разовый таймаут | повтор позже, в заключение не выносится |
| **Не определено** (`unknown`) | признаки противоречат | показать как есть с пометкой «причина не ясна» |

Правило: сетевую блокировку фиксируем только после 2 неудач подряд с интервалом ≥ 1 мин (исключить разовый сбой);
если открываются соседние домены, а этот нет — вероятнее блокировка. Классификатор — таблица признаков,
тестируется на записанных ответах (фикстуры страниц капчи, блокировок прокси, ошибок соединения).

**Заключение при неудаче** (нет «подтверждено» и нет «вероятно»), всегда по-русски:
1. «Не найдено автоматически. Проверено N источников на 3 языках за M с.»
2. **«Можно скачать вручную (сайт защищён от программ)»** — список: сайт, причина (капча / защита от
   скачивания / нужен вход / нужен JavaScript), прямая ссылка на найденную страницу или PDF, а если страницы
   нет — ссылка на поиск этого партномера на этом сайте. Ссылки открываются в браузере по кнопке.
3. **«Нет доступа из сети производства»** — сайты, которые могли бы помочь, но закрыты; кнопка
   «Добавить в запрос администраторам».
4. **«Не проверено: вне белого списка программы»** — ссылки + кнопка «Разрешить домен».
5. Подсказка: «Скачали вручную? Нажмите “Проверить свой PDF”» — файл проходит **тот же** путь:
   карантин → проверка файла → извлечение → улики → вердикт → библиотека (источник `manual`, URL указывает
   пользователь, необязательно). Паспорт документа хранит, что он скачан вручную.
Если что-то найдено, но не подтверждено, пункты 2–4 показываются тоже — как «где ещё посмотреть».

**Список сайтов для администраторов** (таблица SQLite `network_blocks`, накапливается постоянно):
домен, класс, первое и последнее появление, число попыток, для каких партномеров был нужен, пример URL,
ожидаемая польза (уровень источника и его успех по статистике), статус (`заблокирован` / `доступ открыт`).
Отдельной фоновой перепроверки нет (программу запускают эпизодически): статус меняется, когда домен снова
пробуется во время обычного поиска или при ручном запуске «Диагностики».
Экспорт «Запрос на доступ» (TXT и CSV): домены, порт 443, зачем нужны (сколько раз требовались, для каких
чипов), что программа делает (только чтение и скачивание PDF), ссылка на журнал обращений. Список объединяется с
результатами «Диагностики».

## 5. Интерфейс
**Цель:** современный, аккуратный, отзывчивый — не «программа из 90-х». Одинаково на Win7 и на Mac.

**Основа:** PyQt5 Widgets + стиль Fusion + собственная тема QSS, собранная из дизайн-токенов
(`digger/ui/theme/tokens.py`: цвета, отступы 4/8/12/16/24, скругления 6/10, тени, размеры шрифтов).
Две темы — светлая и тёмная — из одних токенов. Шрифты: Segoe UI (Win7) / системный (Mac); китайский —
Microsoft YaHei (есть в Win7) / PingFang (Mac), с запасными вариантами. Иконки — векторный набор под
свободной лицензией (Lucide/Tabler), лежит в `digger/ui/assets/icons`, перекрашивается под тему.

**Компоновка:** слева — список фото карточками с миниатюрой, партномером и цветной меткой («память», «без
памяти», «ищу…», «не найдено»); в центре — карточка чипа (фото/вариант обработки, маркировка, партномер,
корпус); снизу — **живая лента поиска**: строка состояния на языке поиска с меткой EN/CH/RU, плавная
смена текста, счётчики, под ней история по уровням; справа/вкладками — «Заключение», «Документы»,
«Почему» (улики), и вкладки расширений (§6). Сверху — панель действий и **лампочка темы** (горит — светлая,
не горит — тёмная; переключает тему мгновенно, выбор запоминается).

**Отзывчивость (обязательные правила):**
- В потоке интерфейса — никаких сетевых запросов, чтения PDF, OCR, обращений к сетевым дискам (даже
  `os.path.exists` на `\\server` может «подвесить» окно) и SQL дольше нескольких миллисекунд. Всё — в фоне
  (пул потоков), результат — сигналом.
- События поиска приходят пачками: интерфейс обновляется не чаще ~30 раз в секунду (объединение событий).
- Таблицы и списки — через модели (`QAbstractTableModel`/`QAbstractListModel`), не пересоздание виджетов;
  миниатюры строятся в фоне и кэшируются.
- Долгие операции отменяемы; окно всегда реагирует на «Стоп».
- Тест задержки: во время имитации поиска с 1000 событий таймер в потоке интерфейса не должен опаздывать
  больше чем на 50 мс (`tests/ui/test_latency.py`).
- Скриншоты: каждый шаг интерфейса снимает окно в светлой и тёмной теме (`tools/screenshots.py`, offscreen),
  Claude Code их просматривает и проверяет на Mac; снимки кладутся в `my_reports/screens/` (не в git).

## 6. Расширения (новые функции с собственным интерфейсом)
Два уровня модульности:
1. **Роли конвейера** (как в v1): enhancer, ocr, identifier, local_db, acquire, pdf_text, comparator, memory,
   report — замена реализации через `config.json → modules`.
2. **Функции-расширения** (`digger/extensions/` — встроенные, `plugins/` — свои): каждая — папка с
   `extension.json` (id, название, версия, требуемая версия API) и классом `Extension`:
   - `setup(services)` — доступ к сервисам: конфиг, EventBus, локальная база, конвейер, оркестратор поиска,
     фоновые задачи, журнал; собственные таблицы SQLite с префиксом `ext_<id>_` и миграциями;
   - `contribute(ui)` — добавить вкладку, боковую панель, пункт меню, кнопку на панели, страницу настроек,
     колонку в сводке CSV, раздел в HTML-отчёте;
   - подписка на события (фото распознано, поиск начат/завершён, документ подтверждён…).
   Ошибка расширения не роняет программу: оно отключается, пользователю — понятное сообщение.
   Включение/выключение — окно «Расширения» в настройках.
   Встроенные функции делаются тем же способом (проверка API на деле): «История поисков» — база найденных и
   ненайденных чипов, чтобы не искать заново (с кнопкой «искать снова»), «Статистика поиска», «Сайты без доступа»,
   «Замены маркировки» — словарь «прочитано → заменять на», который пополняется ручными исправлениями.
   Крючки конвейера (API 1.1): `services.add_marking_filter(fn)` — `fn(распознанная маркировка) → исправленная`,
   применяется после распознавания (вручную введённый текст не трогает); `services.on_marking_corrected(fn)` —
   `fn(было, стало)` после ручного исправления. Ошибка в крючке отключает расширение, конвейер идёт дальше.
   Версия API расширений — `digger/extensions/api.py`, изменения — только с записью в «Решения».

### 6.1 Распознавание маркировки: сменные провайдеры
Роль `ocr` становится **менеджером провайдеров** (`digger/recognition/`), а каждый способ распознавания —
отдельный провайдер. Добавить новый (локальный продукт, другая модель, облако) = одна папка, без правки программы.

```
recognition/api.py        OcrProvider: id, title, kind (local|cloud), languages, wants_original,
                          is_available() -> (bool, причина), recognize(image_variants, hints, progress) -> OcrResult
recognition/manager.py    RecognitionManager (роль `ocr`): цепочка при неудаче, учёт времени; провайдер ищется
                          по id: recognition/providers/<id> или plugins/ocr_<id>/provider.py, класс Provider
recognition/providers/ppocr/       PP-OCRv4 (rapidocr-onnxruntime 1.3.24 + onnxruntime 1.11.1) — основной; читает
                          исходное фото без улучшения OpenCV, поворот 0/90/180/270 — по лучшей суммарной
                          уверенности; модели грузятся при первом распознавании (в фоне, не при запуске окна)
recognition/providers/tesseract/   запасной: весь код Tesseract здесь (поворот, варианты от enhancer, голосование)
recognition/providers/cloud_stub/  заглушка облака: is_available() = «не настроено»; удаляется вместе с папкой
plugins/ocr_<имя>/                 сторонние провайдеры (provider.json + provider.py)
```
**Единый результат** `OcrResult`: строки с уверенностью 0–100 и рамками, лучший текст, id провайдера,
время, вариант изображения, для облака — примерная стоимость. Провайдер получает уже улучшенные варианты
изображения от `enhancer` (или исходное фото — если провайдеру это лучше, флаг `wants_original`) и
подсказки: ожидаемый алфавит, корпус.

**Выбор в интерфейсе** (карточка чипа и настройки): «Авто» / конкретный провайдер / «Сравнить все доступные».
Кнопка «Распознать заново другим способом» на карточке. В заключении указано, каким способом прочитано.

**Сделано в шаге 0.8:** цепочка `["ppocr", "tesseract"]`; следующий провайдер пробуется, если текущий недоступен,
упал или ничего не прочитал; параметры PP-OCR — `recognition.providers.ppocr` (`text_score`, `det_box_thresh`,
`det_unclip_ratio`, `rotations`); `OcrResult.provider / provider_title / seconds`; исходное фото передаётся в
`OCR.recognize(..., original=)`. Порог уверенности, рамки, выбор в интерфейсе, сравнение — шаги 7.x.

**Сделано в шаге 7.1a:** код Tesseract целиком в `providers/tesseract/` (`modules/ocr_tesseract.py` удалён).
Сторонний провайдер — папка `plugins/ocr_<имя>/`: `provider.json` (`id`, `title`, `kind`) и `provider.py` с классом
`Provider(OcrProvider)`; работает, когда его id стоит в `recognition.chain`, настройки — `recognition.providers.<id>`.
Менеджер читает только описания (`catalog()` — все известные провайдеры для списка в окне); код провайдера вне
цепочки не выполняется, сломанный — пропускается с причиной, id встроенного занять нельзя.
**Объединение:** `OcrResult.attempts` — попытки цепочки (`OcrAttempt`: провайдер, исход `ok`/`empty`/`failed`/
`unavailable`, время, число строк, причина); итог — от провайдера, давшего текст, строки остальных отработавших
добавляются следом без повторов (`OcrLine.provider`) как запасные варианты партномера; `seconds` — время
провайдера-победителя, `total_seconds` — всей цепочки. **Учёт времени:** `RecognitionManager.stats` — по
провайдеру вызовы, исходы и суммарное время (в памяти, на сеанс).

**Сделано в шаге 7.1b:** правила «Авто» — `recognition.auto` (`min_confidence` 60, `require_confirmed` — по
умолчанию **false**, см. «Решения»: переход «не подтвердился справочником» включается настройкой).
Уверенность результата — средняя по строкам итоговой маркировки (`OcrResult.confidence`); подтверждение —
менеджер спрашивает роль `identifier` и смотрит `Candidate.confirmed_by` (справочник / каталог / локальная база;
`OcrResult.confirmed`). Исходы попытки: `ok`, `weak`, `unconfirmed`, `empty`, `failed`, `unavailable`, `no_consent`.
Если не справился никто — берётся результат, подтверждённый справочником, иначе первый по цепочке, кто что-то
прочитал (поэтому порядок цепочки по-прежнему решает). Ход — события `ocr.*` на общей шине (всегда по-русски),
тот же текст идёт в `progress`. Облако: провайдер с `kind: cloud` вызывается, только если `recognition.cloud_enabled`
= true, он сам доступен и `CloudConsent` (`recognition/consent.py`) получил ответ «это фото» или «до закрытия
программы»; вопрос задаёт окно (`gui/worker.py: ConsentBridge` — фоновый поток ждёт ответа из потока окна), без
окна ответ всегда «нет»; согласие в `config.json` не пишется. `providers/cloud_stub/` — заглушка («не настроено»),
в цепочку по умолчанию не входит. Белый список доменов и «только вырезка чипа» — обязанность настоящего облачного
провайдера (сеть только через `netsafe`).

**Сделано в шаге 7.1c:** способ распознавания — `RecognitionManager.recognize(..., mode=)`: `auto` (цепочка), id
провайдера (только он; провайдер не из цепочки создаётся при первом выборе), `compare` (все известные провайдеры
по очереди; итог — первый справившийся, что прочитал каждый — в `OcrAttempt.text`). Способ по умолчанию —
`recognition.mode` (окно «Настройки»), неизвестное значение → «Авто». `modes()` — список для окна; конвейер:
`analyze_image(..., ocr_mode=)`. В окне: строка «Способ» на карточке (список + «Распознать заново»), выбранный
способ действует и для кнопки «Распознать». В заключении — «Способ распознавания: …» с уверенностью и временем,
а если пробовали несколько способов — таблица попыток (`OcrResult.mode`, `attempts`).

**Цепочка «Авто»** (порядок в `config.json → recognition.chain`, по умолчанию только локальные):
провайдер считается не справившимся, если уверенность < порога (по умолчанию 60) или ни один кандидат
партномера не подтвердился справочником/каталогом/локальной базой. Тогда пробуется следующий.
Облачные провайдеры в цепочку по умолчанию **не входят**.

**Облако и безопасность** (дополняет §8 п.4): фото уходит наружу только если (1) облачный провайдер включён
в настройках, (2) его домен в белом списке, (3) пользователь подтвердил отправку — для конкретного фото
(«Отправить фото в <сервис>?») или один раз «для этой сессии». Отправляется только вырезка чипа, без
метаданных файла. Ключи — только в `config.json`. Каждая отправка — в журнал обращений.

**Сравнение провайдеров**: `tools/ocr_bench.py` прогоняет фото из `my_test/ocr/` (рядом `ответы.csv`:
файл → правильная маркировка/партномер) через все доступные провайдеры и строит таблицу: точность
символов, точность партномера, время, стоимость → `my_reports/ocr_bench_<дата>.md`. По ней выбирается
порядок цепочки. Облачные провайдеры бенч не вызывает. `--params` и `--variants` добавляют таблицы наборов
параметров PP-OCR и способов обработки фото перед ним. Статистика «кто справился» копится и в работе (как §4.10 для поиска).

## 8. Безопасность (не ослаблять)
1. Сеть только через `core/netsafe.py`: белый список доменов, каждый редирект проверяется заново, только HTTPS
   (исключения явно в конфиге), проверка сертификатов, запрет IP/локальной сети/нестандартных портов/`file://`.
2. Лимиты размера и времени; вежливая частота запросов; уважать `robots.txt` для прямых страниц каталогов
   (настройка, по умолчанию вкл.); без обхода капчи; постоянный честный User-Agent с именем программы.
3. Всё скачанное — в карантин; ничего не открывать и не исполнять автоматически; PDF читать только pypdf.
4. В сеть уходит только партномер/маркировка. Фото — только в облачный провайдер распознавания и только
   по явному согласию пользователя (§6.1); файлы пользователя — никогда.
5. Cookies только в памяти; ключи API — только в `config.json` (не в git).
6. Журнал `logs/network_audit.log` всех обращений; «Диагностика» формирует запрос для администраторов.

## 9. Тестирование
- **Юнит-тесты** каждого этапа §4.1 (pytest, без сети).
- **Контрактные тесты адаптеров**: `tests/fixtures/sources/<adapter>/<query>.html` + `meta.json`
  (URL, дата, кодировка). Страницы записывает `tools/record_fixture.py` (на машине с интернетом) и урезает
  до выдачи. Тест проверяет: сколько Lead найдено, первые URL, раскодирование переадресаций.
- **Синтетические PDF** (генерируются в тестах): правильный datasheet, datasheet семейства с `x`,
  app note, каталог дистрибьютора, чужой партномер, скан без текста, китайский datasheet, PDF с JavaScript.
- **Статистика**: тесты на синтетической истории поисков — порядок меняется в ожидаемую сторону, разведка
  не пропадает, сглаживание не даёт одному случайному успеху перевернуть порядок.

## 10. Детали, которые легко упустить
- Партномер ≠ маркировка: на мелких корпусах код (SMD-код), на крупных — усечённый партномер без суффикса.
- Datasheet часто общий на семейство (`x`, `/`, перечисления `_02_04_08`), заказной код — в таблице Ordering.
- Перемаркированные и поддельные чипы: противоречие фото и документа — это тоже результат (показать, а не скрыть).
- Китайские аналоги с тем же названием у разных производителей (24C02 — десятки фабрик): несколько
  подтверждённых документов допустимы, выбирается по логотипу.
- Кодировки страниц: GB2312/GBK → GB18030, windows-1251.
- Поисковики оборачивают ссылки (DDG `uddg`, Bing `u=a1…`, Baidu `mu`), результаты меняются — поэтому фикстуры и `live_check`.
- Windows 7: TLS 1.2 обеспечивает сам Python (OpenSSL), а не система; сертификаты — из certifi, не из Windows.
- Антивирусы могут ругаться на exe от PyInstaller — предпочтительно запуск через venv.
- Авторские права: скачанные PDF и сохранённые страницы — не в публичный репозиторий. Репозиторий — **приватный**.
- Сетевая папка может быть недоступна — работать без неё, не падать.
